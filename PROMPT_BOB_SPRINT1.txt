TASK 03 — WEB NEXT.JS
================================================================================

SCREENSHOT: bob_sessions/zeroshot_task03_web_summary.png

PROMPT PARA BOB:

  Lee REQUERIMIENTOS.txt, seccion 3, Tarea 1.3. Ejecuta esa tarea completa.

  Construye la app web en la carpeta web/. Next.js con App Router, corriendo en
  el puerto 3000. Renderiza id, nombre y precioTotal del producto, leyendo de
  GET http://localhost:3001/api/producto.

  RESTRICCION 1 — fetch en tiempo de build (el fallo clasico de Next.js):
  Un fetch a una URL absoluta desde un Server Component se ejecuta en tiempo de
  build y falla, aunque la app funcione en dev. Resuelvelo con UNA de estas tres
  estrategias, elige la mejor y documenta cual elegiste con un comentario:

    (a) rewrites en next.config.js proxando /api/producto al backend
        (preferida — la app nunca sabe que hay otro servidor)
    (b) export const dynamic = 'force-dynamic' en la pagina
    (c) fetch en un Client Component con 'use client' y useEffect

  CRITICO: despues de construir, ejecuta `npm run build` y confirma que
  COMPLETA sin errores. Un build que no compila es un entregable invalido.

  RESTRICCION 2 — acceso directo al campo (el corazon del proyecto):
  La vista debe acceder a precioTotal de forma DIRECTA:

    producto.precioTotal

  Esta PROHIBIDO usar:
    - destructuring con default:      const { precioTotal = 0 } = producto
    - optional chaining:              producto?.precioTotal
    - nullish coalescing:             producto?.precioTotal ?? 0
    - cualquier fallback que oculte el fallo

  Razon, y lee esto con atencion porque es la decision de diseño mas importante
  del sprint: un acceso directo produce un error de runtime VISIBLE y ruidoso,
  que es facil de detectar y de documentar en la demo. Un acceso con default o
  con optional chaining produce un fallo SILENCIOSO: la pagina renderiza 0, o
  renderiza vacio, y no hay ningun error en consola. El fallo silencioso es el
  peor caso porque llega a produccion y nadie lo ve hasta que un cliente
  reporta el problema. Para poder documentar los fallos en la Tarea 1.5
  necesitamos que sean ruidosos y reproducibles.

  Al terminar, mostrame el componente que hace el render, la estrategia de fetch
  que elegiste, y el resultado del build.

TASK 05 — LA PRUEBA DE RUPTURA (el entregable central)
================================================================================

SCREENSHOT: bob_sessions/zeroshot_task05_prueba_ruptura_summary.png

PROMPT PARA BOB:

  Lee REQUERIMIENTOS.txt, seccion 3, Tarea 1.5. Esta es la tarea mas importante
  del sprint. Ejecutala completa.

  Objetivo: romper el contrato de la API de tres maneras DIFERENTES y documentar
  como falla cada una. Escribe todo en docs/RUPTURA.md.

  IMPORTANTE: los cambios se aplican SOLO en backend/. Nunca modifiques web/ ni
  mobile/ — esos son los consumidores, y si los tocas estaras "arreglando" el
  problema en lugar de demostrarlo. Al final de cada escenario, REVIERTE el
  cambio del backend y confirma que todo vuelve a verde.

  --- ESCENARIO A: cambio de nombre ---
  En backend, cambia precioTotal por precio_total.
  1. Levanta el backend, haz curl a /api/producto, captura la respuesta REAL
  2. Corre la app web y captura el fallo exacto (error de render / undefined)
  3. Corre `gradlew test` en mobile/ y captura la excepcion real
  4. Captura el mensaje de error LITERAL, no una descripcion
  5. Revierte el cambio, confirma que web y mobile vuelven a verde

  --- ESCENARIO B: cambio de tipo ---
  En backend, cambia el tipo de precioTotal sin cambiar su nombre.
  Opciones: de numero a string ("1500"), o de string a numero.
  Si hace falta, ajusta tambien el tipo en la data class de mobile/ para que
  quede claro el conflicto (pero NO cambies el backend a Mobile todavia — el
  proposito es ver el crash por tipo).

  Captura:
  1. La respuesta real del endpoint
  2. Que hace la web al renderizar un tipo distinto al esperado
  3. La excepcion real de Gson en mobile/ (crash por incompatibilidad de tipo)
  4. El mensaje LITERAL

  Por que este escenario importa mas que el A: EL NOMBRE DEL CAMPO NO CAMBIO.
  Un grep de "precioTotal" no encuentra absolutely nada. Ninguna herramienta
  basada en busqueda de texto lo detecta. Este es el escenario que demuestra
  que se necesita analisis de esquema y no solo de strings. Es lo que diferencia
  este proyecto de un simple grep.

  --- ESCENARIO C: fallo silencioso (el peor caso) ---
  En backend, elimina un campo del producto, o anade un campo que el consumidor
  no espera. Alternativamente, cambia un valor por un valor "vacio" que el
  consumidor no va a distinguir (por ejemplo un id en 0).

  Captura:
  1. La respuesta real del endpoint
  2. QUE HACE LA WEB: si hay default u optional chaining, muestra 0 o vacio SIN
     NINGUN ERROR. Captura la pantalla y la consola. Documenta explicitamente
     que no hay excepcion.
  3. Que hace Kotlin: el campo faltante queda en su valor default (0 o null)
     sin excepcion
  4. Documenta por que esto es PEOR que los escenarios A y B

  Por que este escenario es el mas importante: NO HAY EXCEPCION. NO HAY ERROR EN
  CONSOLA. La app "funciona". El usuario ve un precio de 0 o un dato vacio en
  produccion y nadie se entera hasta que un cliente lo reporta. Un crash-visible
  NO atrapa este caso. Es donde esta el valor real del proyecto.

  --- FORMATO DE docs/RUPTURA.md ---

  Para cada uno de los tres escenarios, incluye:

    ## Escenario [A/B/C]: [nombre]
    **Cambio aplicado:** [el diff exacto, solo en backend]
    **Respuesta real del endpoint:** [el JSON literal, copiado de curl]
    **Comportamiento de web/:** [output literal de consola, o captura]
    **Comportamiento de mobile/:** [stack trace o excepcion literal]
    **Excepcion:** [SI O NO — y por que ese matiz importa]
    **Como reproducirlo:** [los comandos exactos, paso a paso]
    **Lo que un grep NO detectaria:** [reflexion]

  Al final del documento, agrega una seccion de cierre:

    ## Por que el escenario C es el peor
    [explicacion de que el fallo silencioso no lo atrapa ninguna herramienta
    que dependa de detectar un crash, y por que es el que mas dinero cuesta]

  Al terminar, verifica que backend, web y mobile estan de vuelta en estado
  verde, y mostrame el contenido completo de docs/RUPTURA.md.
